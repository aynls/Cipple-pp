## 三个确认点

1. **发布者收到成功。** 源节点完成配置版本、回放日志和目标 ACK 行的同一 SQLite 事务。对同一个已有 UUID 和相同请求内容的重试返回成功。相同 UUID 配不同内容会被拒绝。结果不明确时向原节点重试，避免一个 UUID 在互不通信的节点上分别生成两个版本。
2. **发送端记录副本确认。** 接收节点完成持久化后发送响应。收到一模一样的实体版本时可以回重复确认。发送端只接受该目标会话中同一请求 UUID 的成功或重复响应。收到拒绝、链路写出、关闭连接和超时都保留待确认记录。有效回执进入本地确认队列，批量落盘失败时重试该事务。发送端若在确认落盘前重启，会重新发送数据库中仍待确认的版本。
3. **订阅端确认。** 持久订阅客户端在同一事务保存事件和本端点的游标，随后回确认。断开后用该端点的游标续传。首次连接另一个端点时从头补齐，已保存 UUID 不会重复施加。应用日志是可观察输出，SQLite 事务内的事件与游标是持久交付记录。

## 分区、顺序与恢复边界

分区期间各节点可确认本地写入。链路恢复且持久数据仍存在时，各节点持续发送尚未确认的版本，按同一顺序解析结果。副本的追加顺序用于订阅回放，版本的 HLC 顺序用于决定当前值。分区晚到的历史事件仍进入回放，订阅端的当前值保持按版本顺序选择。一个在全序中更晚的并发写可以覆盖删除。

部署采用固定成员、稳定节点端点和同一持久卷上的数据库。节点被永久移除、端点换成另一份数据库时，部署方需要重新建立副本数据和客户端端点游标。首次启用持久订阅可读到该键在副本上保留的历史。跨离线期逐条补发需要保留这些日志和增量基底。原版 Java 与 C++ 使用各自的客户端和线上协议。

C++ 运行时保留完整回放日志。M4 SQLite 的保留记录会在打开时建立日志，旧库中的已回收负载仍以原来保留的内容为准。一个从 M4 迁移的单节点数据库可以直接继续使用。把旧单机数据引入新集群时，由发布方重新向集群发布需要迁移的当前配置。

服务端首次打开 `user_version` 为 0 或 1 的数据库时，在同一事务中填充待确认索引并升级到版本 2。已有的回放序号和确认值继续有效。只支持版本 1 的服务端程序无法打开升级后的文件。

如果过去的漏投已使持久游标越过缺失事件，需从更早的游标重放。停止该客户端后，可以在其状态库中清除 `client_cursor` 里对应端点和键的游标，保留 `client_event`。重连时从该副本保留历史的开头补发，先前保存的 UUID 仍参与去重。

Java 的树形、Expander、哈希副本组、客户端辅助扇出和 CPU 感知选点分别影响传播路径或负载分布。候选部署采用全成员传播和直接推送，客户端可顺序或按键哈希选择连接。带有上述路径约束或 Java API 绑定的应用需要对应调整。

## 线上扩展

帧由大端四字节 body 长度及 body 组成，body 以一字节消息类型和 16 字节请求 UUID 开头。长度上限 16 MiB。字符串用大端八字节长度前缀编码。业务实体包含独立 UUID、键、操作、版本与源节点 ID。原有编号保留。

Java 参考同样带四字节长度前缀。其 `ServerChannelInitializer.java:107–108` 和 `ClientChannelInitializer.java:99–100` 使用 Netty 的长度解码器与前缀编码器。Java 使用 36 字符 UUID 和四字节字符串长度。C++ 将 UUID 编码为 16 字节并使用自己的消息字段布局。

| 类型 | 尾部扩展 |
| --- | --- |
| `SyncRequest` 4 | `from_id` 后可附完整基底实体。增量的完整基底和新版本可以在接收端一起提交 |
| `SyncResponse` 5 | 0 成功，1 同实体重复，2 拒绝 |
| `SubscribeRequest` 12 | 空回调地址与 0 回调端口选择同一会话。可选的大端 i64 表示已处理序号，0 从键的完整保留历史开始 |
| `DispatchRequest` 18 | 可选的大端 i64 副本追加序号。0 表示即时事件。序号后可以携带完整基底 |
| `DispatchResponse` 19 | 请求 UUID 与对应分发关联，布尔值表示订阅端处理结果 |

打包 HLC 的版本字段使用 `2^62 + physical_ms * 65536 + logical`。旧 M4 SQLite 记录继续按原数值参与排序，服务端打开旧库时为保留版本建立回放序号。
