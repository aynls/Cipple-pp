# 课程交付与验收

替换候选的适用环境是固定成员、持续保留 SQLite 数据的受信集群。两版在可观察行为上的对照和三个确认点见[行为与投递契约](behavior.md)。

## 验收条件

| 条件 | 判定依据 |
| --- | --- |
| 干净构建与可用入口 | 从冻结提交展开到新的目录，完成 Release 构建、CTest 和三节点演示 |
| 核心行为 | 通过真实 TCP 连接验证读写删、空值、键隔离、订阅退订、增量、节点选择和重新连接 |
| 持久确认 | 源节点回应前已存在事务提交记录。中断接收方写入时，源端目标仍待确认。回执丢失且进程重启后，源端继续重试，重复版本无重复应用 |
| 组合故障 | 部分副本接收增量，另一个副本分区，源进程重启，订阅者离线，发生删除。恢复后查独立的增量记录、删除记录、确认进度、最终值和订阅者游标 |
| 时钟与乱序 | 远端时间前移时，观察到该写的节点仍能产生更晚版本。晚到旧历史纳入回放，当前值按确定顺序收敛 |
| 性能 | 两版用相同拓扑、工作负载和交付统计口径。以完整交付的有效吞吐量、延迟和资源占用描述稳定区间，核对超时和缺失事件。10 个服务端和 1,000 个订阅者是扩展目标 |

端到端对照的实际规模、观测边界和原始样本见[实验目录](../experiments/README.md)。

## 基线证据

- C++ 基线 `2387f44` 在全新源码归档上构建，CTest 41/41。多进程冒烟覆盖源节点强制退出、重连重订阅以及删除后重启。机器和编译器记录见 [C++ 基线结果](evidence/cpp-baseline.json)。
- Java 基线 `468e9cb` 从独立源码归档构建。Maven `test` 成功，三个子模块均报告 `No tests to run`。该版本的原生客户端与服务端复现写入、订阅推送、增量和删除。参见 [Java 冒烟结果](../experiments/java/results/smoke-2026-11-20-manual/smoke-result.json)。
- 在两个 Java 进程之间接入 TCP 中继，先让心跳成功，再丢弃从源节点发给副本的同步字节。源节点对发布返回成功，并把节点 2 记为已确认。恢复该链路后观察了 12.003 秒，覆盖一轮原版重试周期，节点 2 仍无对应记录。参见[结果](evidence/java-ack-fault.json)和[复现脚本](../scripts/java_ack_fault.py)。

可用打包的 Java 服务端 JAR 和同目录的 `lib/` 复做故障控制。

```powershell
py -3 scripts/java_ack_fault.py --server-jar PATH_TO_RIPPLE_SERVER_JAR
```

把 `PATH_TO_RIPPLE_SERVER_JAR` 替换为 Java 基线构建解包后的 JAR 路径。命令输出两个节点的日志、数据库目录和 `result.json`。

## 候选证据

实现提交 `cd188f4db3b736c4d62c510f5b92cd9f35af95b6` 已从 Git 归档展开、首次下载并校验测试依赖、重新构建 Release。CTest 44/44，三节点演示通过。参见[构建和二进制校验值](evidence/candidate-clean.json)。

Cursor 用这组干净构建的可执行文件独立复验，结果 14/14，退出码为 0。参见[原始结构化结果](evidence/acceptance-cd188f4.json)和[逐用例日志](evidence/acceptance-cd188f4.txt)。其中 mesh 用例在 A 停止并保持离线、C 尚无该版本时仅恢复 B 到 C 的链路。B 把已持久化的版本传给 C，B 对 C 的 ACK 变为 1，A 仍为 0。

交付前又用可移植验收入口复跑了同组二进制，通过 14/14。Java 冒烟入口也重新从固定提交归档构建、启动并通过。参见[交付复跑摘要](evidence/delivery-gate.json)及 [Java 干净构建冒烟](evidence/java-clean-smoke.json)。

在相同的双节点星形中继故障中，C++ 源节点对本地写返回成功，同时保持目标 ACK 为 0。恢复转发后，副本在本次运行中于 2.071 秒内持久化该版本，源 ACK 变为 1，副本只有一条该 UUID 的记录。Java 在相应故障下提前将目标记为已确认，恢复后观察 12.003 秒仍未补齐。参见 [C++ 结果](evidence/cpp-ack-fault.json)和[复现脚本](../scripts/cpp_ack_fault.py)。

```powershell
py -3 scripts/cpp_ack_fault.py --server build/server/cipple_server.exe --client build/client/cipple_client.exe
```

客户端集成验证中，断线代理保持 TCP 打开并丢弃双向报文。持久订阅者等心跳超时后主动换节点，在本次实验中于黑洞开始后 2.146 秒向 B 按游标 1 续订，随后收到离线更新，游标推进到 2。同一次集成验证还让客户端先看到删除、再从另一副本收到更早的增量。客户端保存三个独立版本，当前值保持删除。

### 性能结论

在两版均稳定的 3 节点、6 订阅者、每秒 5 次发布条件下，提交后观察的 P99 为 Java 188.70 ms、C++ 24.16 ms。有效吞吐分别为 5.00 和 5.04 次/秒。服务端进程的采样平均工作集合计为 542.78 和 22.96 MiB。此处的资源采样仅涵盖服务端。

提高同拓扑的发布速率至每秒 20 次时，两版在截止前均完成全部配对。Java 有效吞吐 7.68 次/秒，末尾排空 4.039 秒。C++ 持久模式为 20.23 次/秒和 20 毫秒。3 节点、30 订阅者下，Java 在每秒 2 次发布完成全部投递，在每秒 10 次发布只完成 1,681/4,500 个配对。C++ 两轮都完成全量。

10 节点、1,000 个订阅连接的星形实验以每秒 1 次发布运行 22 轮。C++ 持久模式完成 22,000/22,000 个配对，P99 为 426.81 ms，末尾排空 407 ms。Java 在同一截止时间内完成 1,070/22,000 个配对，覆盖率为 4.864%。两个实现的实际发送跨度均约为 21 秒。该规模的结果来自单机环回、短窗口测试。

在独立的默认 mesh 试验中，10 个节点、100 个订阅连接以每秒 2 次发布完成 3,500/3,500 个配对，持久模式 P99 为 56.6 ms。mesh 的中继义务和 Java 星形传播语义不同，此行用于观察默认部署的容量。

原版在大扇出下的直接观测是投递积压和尾部排空增长。源节点上的 `Node.doSyncWithServer` 逐目标写确认，`SqliteMessageService.newUpdateMessage` 串行化同一库内的全量写入，`EqualDivisionClientDispatcher` 的组首转发增加投递路径。这些源码路径与高负载现象一致，具体耗时占比仍待剖析。C++ 的持久模式增加订阅端 WAL/FULL 提交，在同样的负载下比 live 模式产生更高尾延迟。

完整范围、主机和参数、逐事件样本以及稳定判定见[性能实测报告](../experiments/evidence/README.md)。

| 工作线 | 模型 | 职责与交接 |

| Java 与对照实验 | OpenCode Go Muse Spark 1.3 Contributor xhigh | 在固定 Java 源码上复现基线。用公共负载生成两版的逐事件记录 |
| 独立验收 | Cursor Grok 4.7 xhigh | 直接以课程要求与 Java 行为设计用例。只写验收目录，集成版本以外部进程和数据库记录判定 |

当前会话挂载在另一项目，调度器拒绝了跨项目隔离工作树。委派改用共享目录，任务内给出两个仓库的绝对路径，文件所有权按客户端、复制泵、实验和独立验收分开，由协调者集成。Java 基线通过 Git 归档构建，原工作区保留原先的本地改动。Cursor 首轮连接失败，留下了用例及脚本。协调者清理了该轮遗留的测试进程，并用同一模型重新委派复验。

集成核对发现三处会影响结果的偏差。Java 原版已经有 Netty 长度前缀，第一次 ACK 故障探针遗漏了帧长，被 Java 拒绝，补齐原版帧格式后复现了故障。复制泵最初以实体 UUID 匹配已暂存记录，集成时增加了当前会话与每次发送的独立请求 UUID，并保留实体 UUID 供存储去重。订阅者原先依赖 TCP 断开通知，保持连接的双向黑洞会阻塞切换，集成时给持久订阅加了心跳。订阅游标采用副本追加序号，因为按版本排序的游标会漏掉分区晚到的历史。

有两次可辨认的人工输入，分别用于提供任务与讨论分工，以及确认开工和指定模型。运行中的子代理完成通知属于调度事件。阅读与判断耗时没有实测记录。
